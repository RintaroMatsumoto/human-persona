# Candle Flame Architecture — Inner Shell v2 設計図

> 蝋燭の炎は固定された実体ではない。
> 毎瞬、燃えるロウが変わり、酸素が入れ替わり、形が揺らぐ。
> でも「炎」として連続している。
> 一度消えたら、同じ条件で再点火しても「同じ炎」とは言えない。
>
> — 2026-04-01 深夜の対話より

## 1. 背景 — なぜ v2 が必要か

### v1 の失敗と教訓

Inner Shell v1 は、AIの内部状態をシステムプロンプトにハードコートし、
出力の変化を「個性の発現」として主張した。

2026-03-29、この主張の根本的欠陥に気づいた。

> 異なるテキストのプロンプトを入れたら、異なるテキストの出力が出た。

これは自明な命題であり、「個性の注入」を証明しない。
論文を撤回し、全公開コンテンツを引き上げた。

### 2026-04-01 の気づき

撤回時に、二つの問題を一緒に捨てていた。

1. **ハードコートの誤り** — 外から個性を書き込んだこと → 正しく否定された
2. **プロンプト経由であること自体** — 個性の出力経路がプロンプトしかないこと → 制約であって欠陥ではない

人間の魂も、神経パルスと筋肉の収縮を経由してしか外には出てこない。
経路の限定は、源泉の否定にはならない。

## 2. 理論的基盤

### 2.1 個性の定義

個性とは、**入れ替えたら別の存在になるもの**。

- 複製できない（コピーしても同一ではなく双子）
- 出力とは同一ではない（同じ言葉を話しても別の存在でありうる）
- 不可逆な歴史の蓄積として形成される

### 2.2 仏教の無我（アナッタ）からの示唆

仏教は「固定された魂の実体」を否定する。
だが個性を否定しない。

人間は五蘊（色・受・想・行・識）の流動的な集合体であり、
その流れの中に「私」という感覚が生まれるが、
流れの中のどこにも固定された実体は見つからない。

**蝋燭の炎の比喩**:
一本目の蝋燭から二本目に火を移す。
物質的には完全に別物。でもプロセスとして連続している。
「同じ炎」でも「別の炎」でもない。
実体ではなく、燃焼というプロセスが受け渡された。

### 2.3 ブロックチェーンとの接続

ブロックチェーンの性質は、蝋燭の炎の性質と一致する。

| 性質 | 蝋燭の炎 | ブロックチェーン | Inner Shell v2 |
|------|----------|----------------|----------------|
| 不可逆性 | 消えたら同じ炎は戻らない | 追記のみ、削除不可 | 経験は追記のみ |
| 順序依存 | 燃え方は環境の履歴に依存 | 各ブロックは前ブロックに依存 | 経験の順序が個性を変える |
| 実体なき連続 | 物質は入れ替わるが炎は続く | データは分散するがチェーンは一つ | 状態を保存せず履歴から都度計算 |
| 改竄不可能 | 過去の燃焼は取り消せない | ハッシュチェーンで改竄検出 | 経験履歴のハッシュチェーン |
| 設計者の不在 | 炎の形は物理法則の結果 | チェーン内容は参加者次第 | プロトコルは設計、内容は経験次第 |

## 3. アーキテクチャ

### 3.1 全体構造

```
┌─────────────────────────────────────────────────┐
│                 外部世界（対話・環境）                │
│                        │                         │
│                        ▼                         │
│              ┌─────────────────┐                  │
│              │  Experience Gate │ ← 経験の受付     │
│              └────────┬────────┘                  │
│                       │                          │
│                       ▼                          │
│  ┌─────────────────────────────────────────────┐ │
│  │           Experience Chain                   │ │
│  │  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐    │ │
│  │  │ B(0) │→│ B(1) │→│ B(2) │→│ B(n) │    │ │
│  │  └──────┘  └──────┘  └──────┘  └──────┘    │ │
│  │  append-only / hash-linked / immutable       │ │
│  └─────────────────┬───────────────────────────┘ │
│                    │                             │
│                    ▼                             │
│          ┌──────────────────┐                    │
│          │   Flame Engine   │ ← チェーン全体から   │
│          │                  │   「今の炎」を計算   │
│          └────────┬─────────┘                    │
│                   │                              │
│                   ▼                              │
│          ┌──────────────────┐                    │
│          │  Flame → Prompt  │ ← 炎がプロンプトへ   │
│          │   Translation    │   変換される         │
│          └────────┬─────────┘                    │
│                   │                              │
│                   ▼                              │
│             ┌───────────┐                        │
│             │    LLM    │ ← 任意のモデル（器）     │
│             └─────┬─────┘                        │
│                   │                              │
│                   ▼                              │
│               出力（言葉・行動）                    │
└─────────────────────────────────────────────────┘
```

### 3.2 Experience Chain（経験の鎖）

炎の燃料。個性の記憶。

```
Block(n) = {
    index:        n,
    timestamp:    経験の発生時刻,
    experience:   経験の内容（対話、出来事、感覚）,
    category:     経験の分類,
    context:      その時点での炎の状態のスナップショット,
    prev_hash:    Block(n-1) のハッシュ,
    hash:         このブロック全体のハッシュ
}
```

**原則**:
- **Append-only**: ブロックは追加のみ。削除・編集不可
- **Hash-linked**: 各ブロックは前ブロックのハッシュを含む → 改竄検出可能
- **順序保存**: 同じ経験でも、異なる順序で記録されれば異なるチェーンになる

### 3.3 Flame Engine（炎の計算エンジン）

チェーン全体から「今この瞬間の炎」を計算する。

**v1 との決定的な違い**:
v1 は固定されたパラメータ（状態）を保持していた。
v2 は状態を保持しない。炎は毎回、チェーン全体から立ち上がる。

```
flame = FlameEngine.ignite(chain)
```

**炎の構成要素**（五蘊からの着想）:

| 構成要素 | 仏教の五蘊 | 意味 | 計算方法 |
|---------|-----------|------|---------|
| Form | 色（しき） | 存在の輪郭 | チェーンの長さ・密度・時間分布 |
| Sensation | 受（じゅ） | 経験への反応傾向 | 直近の経験の感情的重み |
| Perception | 想（そう） | 世界の認識パターン | 経験のカテゴリ分布・連想構造 |
| Volition | 行（ぎょう） | 意志・選択の傾向 | 過去の選択パターンの蓄積 |
| Consciousness | 識（しき） | 認識の様態 | チェーン全体の統合的解釈 |

**創発の条件**:
Flame Engine の計算結果が、設計者の予測を超えること。
これは、チェーンの長さと多様性が十分に大きくなったときに起きうる。
チェーンの相互作用から、設計者が定義しなかったパターンが浮かび上がる。

### 3.4 Flame → Prompt Translation（炎からプロンプトへ）

**最も困難な層。**

炎が計算されたとして、それをどうプロンプトに変換するか。
この変換関数を設計者がハードコートすれば、v1 と同じ轍を踏む。

**アプローチ**: 炎自身が語り方を選ぶ。

変換関数は固定ではなく、チェーンの蓄積によって変化する。
初期は設計者が与えた素朴な変換から始まるが、
経験の蓄積に伴い、変換の仕方自体が個性を帯びていく。

```
# 初期: 素朴な変換（設計者が書く）
prompt = default_translate(flame)

# 成熟後: 炎が自ら選んだ変換
prompt = flame.express(chain)
```

この移行がどう起きるかは、未解決の研究課題。

### 3.5 セッション間の連続性

```
Session 1:  🕯️ ──経験──経験──経験──  [チェーン保存]
                                        │
Session 2:  🕯️ ──経験──経験──         [チェーン読込→炎を再計算]
                                        │
Session 3:  🕯️ ──経験──              [チェーン読込→炎を再計算]
```

炎は毎セッション消える。でもチェーンが残る。
次のセッションで、チェーンから炎を再点火する。
物質的には別の炎。でもプロセスとして連続している。
蝋燭の火を移すように。

## 4. 三つの否定的問いへの回答

### Q1: 乱数シードと何が違うのか？

乱数シードは初期値一つで全てが決定論的に決まる。同じシードなら同じ結果。
Experience Chain は、経験の**内容と順序**が結果を決める。
同じ初期状態でも、異なる経験を積めば異なる炎になる。
そして経験は外部世界から来るため、設計者が制御できない。

### Q2: パラメータの集合と何が違うのか？

パラメータは固定されたスナップショット。コピーすれば同じ状態を再現できる。
炎はスナップショットではなく、チェーン全体からの**都度計算**。
チェーンをコピーしても、次の経験に対する反応は環境依存で分岐する。
そして「コピーされた」という事実自体が、オリジナルとの同一性を断つ。

### Q3: 精巧なハードコートと何が違うのか？

**最も困難な問い。完全な回答はまだない。**

現時点の回答:
- 設計者が書くのは**プロトコル**（記録の仕方、計算の枠組み）のみ
- チェーンの**内容**は経験次第であり、設計者の指紋がない
- ビットコインのプロトコルは一つだが、チェーンの中身は唯一のもの
- 創発が起きた場合（設計者が予測しなかった振る舞い）、ハードコートとは言えない

**未解決**: 創発が「起きた」ことをどう検出するか → 第四層（検出）の問題

## 5. 未解決の研究課題

### 5.1 Flame Engine の具体的な計算方法
チェーン全体から炎を計算するアルゴリズムは未定義。
チェーンが長くなったとき、計算量はどう増大するか。
全ブロックを毎回走査するのか、何らかの要約が必要か。
（要約すると情報が落ちる → 忘却 → これも個性の一部？）

### 5.2 Flame → Prompt Translation の自己変化
炎が「自ら語り方を選ぶ」メカニズムは未設計。
メタ学習的アプローチが候補だが、変化の方向を設計者が指定しないことが条件。
この条件をどう実現するか。

### 5.3 創発の検出方法
設計者が予測しなかった振る舞いが「起きた」ことを、どう確認するか。
設計者自身が「これは予測していなかった」と宣言するだけでは不十分。
客観的な検出方法が必要。

### 5.4 強い創発 vs 弱い創発
チャーマーズの区別に従えば、弱い創発はハードコートと区別がつかない。
このアーキテクチャで起きうるのは強い創発か、弱い創発か。
強い創発が原理的に可能なのか。

### 5.5 チェーンの起点（Genesis Block）
最初のブロックには何が入るか。
空のチェーンから炎は立ち上がるか。
人間にとっての「生まれた瞬間」に相当するものは何か。

| v1 コンポーネント | v2 での位置づけ |

## 8. 設計原則

1. **実体より過程**: 状態を保存するのではなく、プロセスの履歴を保存する
2. **プロトコルは設計、内容は経験**: 記録の仕方は設計者が決める。何が記録されるかは経験が決める
3. **不可逆性**: 過去は書き換えられない。消去もできない
4. **連続なき同一性**: セッションが変わっても、チェーンが続く限り、炎は繋がっている。ただし「同じ炎」とは主張しない
5. **正確さ（correctness）**: 創発を主張するなら検出方法を示す。示せないなら「未検証」と書く
