## 何が起きたか

[human-persona](https://github.com/RintaroMatsumoto/human-persona) の `core/` には、5つのコンポーネントからなる基底クラスがある。TimingController、StyleVariator、EmotionStateMachine、ContextReferencer、EscalationDetector。言語・文化非依存で設計した、人間らしいAIコミュニケーションのフレームワークだ。

ある日、このフレームワークを使って**実際のプロダクション環境に組み込むための簡易パイプライン**を書いた。`humanize/pipeline.py` ——フィラー注入、タイポ注入、リズム変動の3ステージで構成した後処理パイプラインだ。

書いた。テストした。ベンチマークも通した。

**そして凍結した。**

この記事は「なぜ自分で書いたコードを自分で凍結したのか」の話だ。

## pipeline.py は何をしていたか

仕組みは単純だった:

```python
class HumanizePipeline:
    def __call__(self, text: str, strength: float = 0.4) -> str:
        sentences = self._split(text)
        sentences = self._inject_fillers(sentences, strength)
        sentences = self._inject_typos(sentences, strength)
        sentences = self._vary_rhythm(sentences, strength)
        return self._join(sentences)
```

1. **フィラー注入**: 文頭に「実は、」「正直なところ、」などを確率的に挿入
2. **タイポ注入**: 「ですが」→「でうすが」のような意図的なタイプミス
3. **リズム変動**: 短い感想文（「これは重要です。」）の挿入で文長にバリエーション

日本語の句点処理にバグがあった（`。。` の二重句点）ので修正し、DPOベンチマークのスコアも問題なかった。

ここまでは順調に見えた。

## 最初の異変：レジスターが存在しない

実際のテキストで Before/After を並べて眺めた瞬間、違和感に気づいた。

パイプラインは**すべてのテキストを同じように処理している**。ビジネスメール、カジュアルなチャット、公式文書——全部同じフィラー、同じタイポ率、同じリズム。

これは根本的に間違っている。

言語学でいう**レジスター**（formal / business / casual / friendly）の区別が一切ない。ビジネスメールで「正直なところ、」は適切かもしれないが、契約書で同じフィラーを入れたら致命的だ。カジュアルなチャットでは逆にフォーマルすぎる。

## 致命傷：日本語の敬語体系

次にもっと深刻な問題が見つかった。日本語の敬語には3つの層がある:

- **尊敬語** (sonkeigo): 相手の動作を高める（「ご覧になる」「いらっしゃる」）
- **謙譲語** (kenjougo): 自分の動作を低める（「拝見する」「参る」）
- **丁寧語** (teineigo): 文末を丁寧にする（「です」「ます」）

pipeline.py はこの区別を一切していない。日本語のフォーマリティをスカラー値 `formality_default: 0.7` で扱っていた。

これでは「対応いたします」（謙譲語・適切）と「対応させていただきます」（過剰謙譲・不自然）の使い分けができない。「ご検討くださいませ」（尊敬語）と「検討します」（丁寧語のみ）の適切な選択もできない。

日本語ネイティブが読めば即座に違和感を覚えるレベルの問題だ。

## 真の問題：自分のコードを読んでいなかった

ここで一番痛い事実を書く。

`core/base_persona.py` にはすでに、これらの問題に対処するための設計がされていた:

- `EmotionStateMachine` は会話フェーズに応じてフォーマリティを自動調整する
- `StyleVariator` は文体パターンを5種類持ち、重み減衰で同じパターンの連続を防ぐ
- `config/ja.json` には `context_level: 0.85`（ハイコンテキスト文化）や `formality_default: 0.7` が定義されている

**pipeline.py はこれらの既存アーキテクチャを完全に無視して作られていた。**

なぜ無視したか？ 正直に言うと「手っ取り早く動くものが欲しかった」からだ。core/ の10段階パイプライン（エスカレーション判定 → 感情更新 → 生成 → 文体変動 → 文脈参照 → 曖昧性 → 後処理 → 遅延）を理解するより、3段階の後処理を書く方が速かった。

速かった。そして間違っていた。

## 機械評価の罠

もう一つ、見逃していた問題がある。

Ablation Study では DPO ベンチマークを使って各ステップの貢献度を測定した:

- フィラー注入: ~60%
- タイポ注入: ~25%
- リズム変動: ~15%

スコアは良かった。でもこの評価自体が問題だった。

**機械評価は表層的な特徴を検出しているだけだった。** フィラーがあれば「人間っぽい」、タイポがあれば「人間っぽい」。でもそれは「人間らしさ」ではない。人間らしさは敬語の適切な使い分け、文脈への自然な参照、感情の一貫した変遷にある。

これらは DPO のスコアには反映されない。

## 方向転換：プロンプトレベルの制御

ではどうするか。2つの事実を整理した:

**事実1**: 単発のテキスト生成（提案文、メールなど）には、感情遷移も文脈蓄積も不要。LLM のシステムプロンプトにペルソナ指示を組み込む方が、後処理パイプラインより効果的。

**事実2**: human-persona の core/ アーキテクチャが本当に必要になるのは、**継続的な会話**のフェーズ。クライアントとの5往復、10往復のやり取りで、感情が変化し、前の文脈を参照し、応答タイミングが自然に揺らぐ——これはプロンプトだけでは制御できない。

つまり pipeline.py は**解くべき問題を間違えていた**。

単発テキストの人間化は、プロンプトレベルの指示で十分だった:

```
文体と人格:
- 丁寧語ベース（です・ます体）。ただし尊敬語の過剰使用は避ける。
  - OK: 「対応いたします」
  - 避ける: 「対応させていただきます」
- 書き出しの一文: 最大20文字。核心を突く。
- 短文と長文の比率: およそ1:3。
```

このプロンプトを DeepSeek API で A/B テストした。結果は明確だった:

| 観点 | 旧（汎用プロンプト） | 新（ペルソナプロンプト） |
|---|---|---|
| 書き出し | 「案件内容を拝見しました。」（定型） | 9文字で案件の核心に切り込む |
| 敬語 | 「させていただきます」過多 | 「です・ます」ベース |
| 文長バリエーション | 均一（3〜4行の文が並列） | 短文と説明文が混在 |
| CTA | 「ご検討のほど、よろしくお願いいたします」 | 「商品数を教えてください」（対話誘導） |

Human Eval（目視評価）でも有効性を確認した。

## 教訓

### 1. 既存アーキテクチャを読め

新しいコードを書く前に、プロジェクトの既存設計を**全部**読む。「読むのに時間がかかるから」は理由にならない。読まずに書いたコードを作り直す方がはるかに時間がかかる。

### 2. 機械評価を過信するな

DPO ベンチマークのスコアが良くても、それは表層的な特徴の一致を測っているだけかもしれない。特に「人間らしさ」のような主観的品質については、Human Eval（人間による目視評価）が不可欠。

### 3. 問題のスコープを見極めろ

「AIの出力を人間っぽくする」は一つの問題に見えて、実は2つの異なる問題だった:

- **単発テキスト**: プロンプトレベルの制御で十分。後処理パイプラインはオーバーエンジニアリング。
- **継続的会話**: プロンプトだけでは不十分。EmotionStateMachine、ContextReferencer、TimingController が必要。5往復を超えると破綻する。

pipeline.py は前者の問題を後者のツールで解こうとしていた——しかもそのツールを使いこなせていなかった。

### 4. 凍結は悪くない

「書いたコードを捨てる」のは気分が良くない。でも間違った方向に進み続けるよりはるかにマシだ。pipeline.py は凍結したが、ここで得た知見（敬語体系の重要性、レジスターの必要性、機械評価の限界）は次の設計に直接活きる。

## 現状と次のステップ

- `humanize/pipeline.py`: **凍結**。保存はするがプロダクション利用はしない。
- 単発テキスト生成: **プロンプトレベルのペルソナ制御**に移行済み。数値制約とプラットフォーム別トーン調整を含む。
- 継続的会話: **未着手**。core/ の基盤を活用した本格的な再設計を予定。
