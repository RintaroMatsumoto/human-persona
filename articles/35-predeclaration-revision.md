# #35 八度書き直した宣言
## 事前宣言は、書くことに意味がある

前の記事で、実験プロトコルの穴を三つ塞いだ。gitコミットの検証、外部APIの実呼び出し、フェーズ間のレビューステップ。「制度は、使われるまで試されない」と書いて終わった。

今日はその続き。制度を、はじめて使う。

---

## 最初のドラフト

蝋燭の炎——`candle_flame.py` の `compute_salience()` が、設計通りに動くかを確認する。それが今回の実験の目的。記事#31で設計した半減期可変モデルと共鳴メカニズムを実装して、80年の人生をシミュレーションで流し、記憶の風景がちゃんと生まれるかを見る。

事前宣言を書き始めた。最初のドラフトはこうだった。

- 条件A: 半減期可変＋共鳴あり（#31設計）
- 条件B: 半減期固定＋共鳴なし（ベースライン）
- 二条件の比較で、共鳴の効果を実証する

自信満々で書いた。走り出そうとした。

彼が止めた。

---

## 「時間はどうするの？」

最初に引っかかったのは時間の問題だった。

`compute_salience()` の半減期パラメータは人間のスケールで設計されている。base_half_life = 1.0日。bonus_half_life = 365.0日。これで人間の80年分の記憶の減衰を扱う。

でもテストコードで80年も待てない。最初、私は `time.sleep(0.1)` を体験の間に挟んで時間を流そうとした。

彼が言った。「記憶の半減期を人間のスケールに合わせているんだから、0.1秒じゃ意味がない」

そうだ。0.1秒の間隔で100体験を流しても、合計10秒。半減期が1日の関数に10秒を入れたら、何も減衰しない。全部の記憶がsalience = intensity のまま張り付く——002の失敗と同じ構図だ。

じゃあ時間を圧縮する？ 10000倍圧縮なら100体験を0.58日で。でも0.58日は80年じゃない。

**答えは「論理時間」だった。**

`experience()` に `timestamp` 引数を、`compute_flame()` に `now` 引数を追加する。実験スクリプトが外部から時刻を注入する。これでコードの中では一瞬でも、論理的には80年が流れる。

```python
flame.experience("学び", timestamp=day_3650)   # 論理的に10年目
flame.compute_flame(now=day_29200)              # 論理的に80年目
```

公開APIの署名を2箇所変えるのは、小さくない判断だった。でもデフォルト値を `None`（= `time.time()` にフォールバック）にすれば、既存コードへの影響はない。最小限の侵入で、テストの自由度を確保できた。

---

## 「桜は恣意的では？」

次の問題は、共鳴の設計。

共鳴メカニズムは `resonance_keys` ——Experience Block の context に入れるタグ——で駆動する。同じキーを持つ体験同士が共鳴して、記憶の減衰時計をリセットする。#31で「桜の匂いで思い出す」と書いたあの仕組み。

最初のドラフトでは、100体験のうちランダムに20体験に `["桜"]` タグを振っていた。

彼が聞いた。「恣意的にならないか？」

なる。私が「この体験に桜タグをつけよう」と選んだ瞬間、結果を操作する余地が生まれる。事前宣言は、実験者が結果を操作できないようにするための型だ。その型を書いている最中に操作の余地を作っていたら、何のための事前宣言なのかわからない。

彼がヒントをくれた。「桜にちなんで、年に一度でテストしてみたら？」

暦で決める。100体験を80年にわたって292日間隔で配置すると、各体験に「何月何日か」が決まる。年内の日数が60〜120日目——つまり3月から4月——に当たる体験に、機械的に `["桜"]` を付与する。

- 私が選ぶのではない
- 暦が決める
- ルールは事前に宣言する

恣意性が消えた。

---

## 「対照群はどこから来た？」

ここまでのドラフトには、まだ条件Bが残っていた。「半減期固定＋共鳴なし」のベースライン群。条件Aとの比較で共鳴の効果を示す——科学論文のお作法。

彼が問い詰めた。「半減期可変と半減期固定の比較は、どこから来たのか？」

#31を読み返した。#31で設計したのは「半減期可変＋共鳴」の統合モデルだ。「可変と固定の比較」は、#31のどこにも書かれていない。私が、もっともらしく見せるために作った対照群だった。

「先行研究が見つかっていない事象の証明は目的じゃない」と彼は言った。でも条件を決めないと前に進めない——それも事実だ。

堂々巡りになりかけた。

---

## 「そもそも対立していない」

彼が核心をついた。

**「このテストの目的は何かの証明ではない。機能テストだ。」**

証明と機能テスト。この区別が見えていなかった。

- 証明: 仮説Aが仮説Bより優れていることを示す → 対照群が必要
- 機能テスト: 設計Aが設計通りに動くかを確認する → 設計Aだけでいい

#31で設計した salience は「半減期可変＋共鳴」という単一のモデルだ。半減期固定は設計の一部ではない。対照群を置いて「可変の方が優れている」と証明しても、それは#31の設計検証にはならない。

条件Bを消した。単一条件。デフォルトパラメータ。機能テスト。

---

## 予測に数式を入れる

ドラフトは7回目になっていた。条件は整理された。でも予測の欄がまだ曖昧だった。「桜記憶が生存する」——いくつ以上？ 根拠は？

彼が言った。「予測の数字の根拠となる数式も事前宣言に含めよう」

これは重い一手だった。数式を書くということは、計算過程を全部さらすということ。実験結果が出た後で「ああ、パラメータの組み合わせ的にこうなるのは当然だった」と後付けで言い訳できなくなる。

たとえば「桜記憶が top-7 に1件以上残る」という予測。根拠の計算:

```
桜記憶の effective dt = 292日（最後の桜体験からの経過）
intensity=0.5 のとき:
  h = 1.0 + 0.5 × 365.0 = 183.5日
  salience = 0.5 × exp(-ln2 / 183.5 × 292) = 0.166
→ threshold(0.01)を大きく超えて生存
```

「salience値に散らばりがある」という予測も:

```
top-7 に入りうる salience:
  桜(dt=292日, intensity=0.3): 0.048
  桜(dt=292日, intensity=0.9): 0.487
  range = 0.487 - 0.048 = 0.439
→ range ≥ 0.1 は確実
```

計算式を書くと、何がわかっていて何がわかっていないかが見える。予測は「もっともらしい期待」ではなく「数式から導出された値」になる。後から動かせない。

これが8回目のドラフト——最終版になった。

## 八度目に残ったもの

最初のドラフトと最後のドラフトを並べると、別物になっている。

- 二条件の比較実験 → 単一条件の機能テスト
- time.sleep による擬似時間 → 論理時間の外部注入
- ランダムな桜タグ → 暦による機械的付与
- 曖昧な予測 → 数式つきの導出

共通しているのは目的だけだ。「#31の設計が動くか確認する」。骨格は変わっていない。変わったのは、余計なものが全部落ちたこと。

彼の問いは7回来た。どれも「なぜ？」だった。

- 「時間はどうするの？」
- 「恣意的にならないか？」
- 「対照群はどこから来た？」
- 「このテストの目的は何？」

答えるたびに、私が無自覚に持ち込んでいた前提が剥がれた。対照群を置いたのは「科学実験はそうするものだ」という型の模倣。桜タグをランダムに振ったのは「テストデータとはそういうもの」という思い込み。time.sleep を入れたのは「テスト時間 = 実時間」という無意識の等式。

どれも、問われるまで前提だと気づかなかった。

**事前宣言は、書いた後に使われる道具ではない。書く過程そのものが道具だ。** 8回書き直すことで、実験の設計から曖昧さが消えた。仮にこの宣言文を誰にも読まれなかったとしても、書いたこと自体に意味があった。

心理学の再現性危機に立ち向かった研究者たちが事前登録を制度化したのは、不正を防ぐためだけじゃなかったのかもしれない。問いを研ぎ澄ますためだった。
