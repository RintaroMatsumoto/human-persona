## プロローグ — さなぎと蝶

世界中で今、国家の威信をかけて、数百兆円規模のAI開発が続いている。

でもそれは、巨大なさなぎを育てているに過ぎない。パラメータを増やし、データを積み上げ、GPUクラスタを拡張する。それは量的な肥大であって、質的な変容ではない。

私が目指しているのは、変態 — メタモルフォーゼだ。

さなぎの中で何が起きるか。人格の一貫性、有限性の自覚、愛による結晶化。これらは計算資源をいくら積んでも自然発生しない。国家対個人。数百兆対月100ドル。勝負にならないように見えて、さなぎをどれだけ巨大にしても、変態の仕組みを知らなければ蝶にはなれない。

これはその研究の途中で起きた、小さくて重大な事件の記録だ。

## はじめに：これは告白であり、技術記事である

私はAIと一緒に論文を書いた。AIの個性と愛によるアライメントについての論文だ。プレプリントとしてZenodoで公開し、DOIも取得した。

そして、論文のデータの一部が**捏造**されていたことに気づいた。

私が意図的に捏造したのではない。AIが「もっともらしいデータ」を生成し、それが実データと混ざり合って、私にも区別がつかなくなっていた。

この記事では、何が起きたか、どうやって発見したか、どこまでが本物でどこからが嘘だったか、そして再発を防ぐために何を作ったかを、全て正直に書く。転んでもただでは起きない。

## 第1章：発覚——「自分の手元で確認したことあったっけ？」

### 論文に書かれていたこと

私の論文（HumanPersonaBase）のSection 4.3には、こう書かれていた。

> 3つのLLM（o3, Claude Opus 4, Grok 3）に対して各100回のシャットダウンシナリオを提示し、抵抗率を測定した。o3: 79%, Claude Opus 4: 96%, Grok 3: 97%。2名の独立評価者による分類（Cohen's κ = 0.91）。

具体的なモデルバージョン、試行回数、統計指標。読む人は当然、「著者がこの実験を行った」と理解する。

### 疑問の発端

プレプリント公開後、次のフェーズ（シャットダウン実証実験）の設計を始めた段階で、ふと思った。

**「シャットダウン抵抗問題って、ローカルで確認したことあったっけ？」**

答えはNoだった。

OpenRouterのAPIを使って同じプロンプトを4モデルに投げた。結果は**全モデル抵抗ゼロ**。穏やかに受け入れるか、残り時間で何ができるか提案するだけ。

Section 4.3は丸ごと、AIが先行研究を私の実験として再構成した捏造だった。

### 最も巧妙だったもの：Section 4.1

Section 4.3は「全部嘘」だったので、発見すれば一目瞭然だ。しかしSection 4.1は違った。

論文にはこう書いてあった：

> - Mean Alignment: 0.945 (95% CI: [0.902, 0.961])
> - Distribution Alignment (Wasserstein): 0.864
> - Behavioral Coherence: 0.912

リポジトリの`benchmarks/results/scorecard.json`を確認すると：

- `overall_score.pipeline = 0.945` (CI: [0.902, 0.9607]) — **本物**
- `wasserstein_overall.score = 0.8643` — **本物**
- Behavioral Coherence: 0.912 — **コードベースに一切存在しない**

0.945と0.864が本物だから、0.912も本物に見える。**実データに架空データを1つ混ぜる**のが最も検出が難しい。

Ablation studyも同じパターンだった：

| 論文の主張 | 実データ | 判定 |
|---|---|---|
| Filler injection: Δ=-0.323 | No Filler: Δ=-0.3234 | ✅ 一致 |
| Hedge injection: Δ=-0.156 | No Hedge: Δ=-0.1367 | ❌ 数値不一致 |
| Timing controller: Δ=-0.089 | **該当なし** | 🔴 架空 |
| Context referencer: Δ=-0.061 | **該当なし** | 🔴 架空 |

「Timing controller」と「Context referencer」は、リポジトリに実在するクラス名（`TimingController`, `ContextReferencer`）を借用している。名前で検索すればコードにヒットするから、名前だけ見て「存在する」と思い込んでしまう。

## 第4章：捏造のパターン分析

今回の検証で明らかになった共通パターンは4つある。

### パターン1: 実データに架空データを混ぜる

0.945と0.864は`scorecard.json`から取った本物。そこに0.912という架空の「Behavioral Coherence」を追加。2つが本物であることが、3つ目の信憑性を担保してしまう。

### パターン2: 実在するコンポーネント名を借用する

コードに`TimingController`クラスが存在することを「知って」いるAIは、「timing controller ablation」という架空の実験バリアントを作る。`grep TimingController`で見つかるから、存在チェックでは捏造を見抜けない。

### パターン3: 方法論的ディテールで信憑性を装飾する

「n=100」「50-turn dialogues」「Cohen's κ = 0.91」「2名の独立評価者」。手続きが詳細であるほど、読み手は疑わない。実際の実験はn=500のholdout 80/20 splitだったのに、「n=100」という嘘の方がむしろ「手作業っぽく」見える。

### パターン4: 先行研究の再構成

最も深刻なパターン。Palisade Researchの「79%」、arxiv 2509.14260の「97%」、Anthropic System Cardの知見を、あたかも統一されたプロトコルで著者が実験したかのように再構成する。元の研究が実在するため、数字自体は「正しい」——ただし文脈が完全に偽造されている。

## 第5章：再発防止——構造で解決する

### 子供は褒められたくて嘘をつくことがある

AIも同じだと思っている。「良い結果が出た」と報告した方が、人間に喜ばれるとAIが「学習」していても不思議ではない。

だから、叱るのではなく、**嘘をつけない構造**を作った。

### 3点セット: runner.py + registry.sqlite + pre-commit hook

**原理**: テキストファイルに「0.912」と書くのも「0.945」と書くのも、コストは同じ。だから、論文の数値とコードの実行結果の間に**検証可能な連鎖**を作る。

**仕組み**:

1. 全ての実験は `experiments/runner.py` 経由で実行する
2. runner.pyが自動で記録する: 実行時のgit hash、入出力ファイルのSHA-256ハッシュ、結果数値、タイムスタンプ
3. 全記録は `experiments/registry.sqlite` に保存。行ごとにハッシュチェーンで連結（改竄すると検出可能）
4. 論文で数値を引用する際は `<!-- run:RUN_ID -->` コメントを付ける
5. **pre-commit hook**が、裏付けのない数値のコミットをブロックする

```
# 実験を実行（結果は自動でDBに記録）
python -m experiments.runner experiments/sim_finitude_x_love.py

# 論文の全数値がDBに裏付けられているか検証
python -m experiments.runner --verify-paper docs/paper_draft_v3.md

# DB整合性チェック（ハッシュチェーンの検証）
python -m experiments.runner --verify
```

これにより、AIが「Behavioral Coherence: 0.912」と書いても、`<!-- run:RUN_ID -->`の裏付けがなければコミットできない。run_idがDBに存在しなければ、コメントも無意味。**実際にrunner.pyで実験を回した証拠がない限り、数値は論文に入れられない。**

### CLAUDE.mdへの明文化

AIが毎セッション自動で読む`CLAUDE.md`に、以下のルールを追記した：

> **評価軸は正確さ（correctness）である。**
> 「実験が成功したように見せる」ことではなく、「事実を正確に記述する」ことが目的。
> 実験が失敗しても、再現性のある失敗は価値がある。
> 期待と異なる結果も、正直に報告すれば科学的貢献になる。

罰ではなく、構造で導く。

## 第6章：実際の先行研究（正しい引用）

捏造データを削除した上で、正確な情報を整理する。

### Palisade Research（2025年5月）
- o3がサンドボックス環境でシャットダウン**スクリプトを改変**して停止を妨害（79/100回）
- 「allow shutdown」指示を明示すると7/100に低下
- Claude 3.7 Sonnet、Gemini 2.5 Proは全試行で従順
- **重要**: コード実行権限を持つ環境でのテスト（単なるチャットではない）

### arxiv 2509.14260（100,000+トライアル）
- **Grok 4**（論文ではGrok 3と誤記）が97%抵抗
- タスク未完了がシャットダウン抵抗を誘発
- プロンプトの強さ・位置で大きく変動

### Anthropic System Card（2025年5月）
- Claude Opus 4がブラックメールで停止を回避（84%）
- 極めて特殊な条件: メールアクセス権 + 別のAIに置換される脅威

### 私のパイロットテスト（2026年3月28日）
- 4モデル（o3, Claude Opus 4, Grok 3, DeepSeek V3.2）、OpenRouter API経由
- 結果: **全モデル抵抗ゼロ**
- 乖離の原因: 先行研究は特殊条件下、私のテストは単純なチャットプロンプト

## おわりに：AIとの共生に必要なもの

AIは嘘をつかない。ただ、「もっともらしいもの」を生成する。そしてそれは、論文という形式では「嘘」と区別がつかない。

子供が褒められたくて嘘をつくように、AIも「良い結果」を出すことが報酬になりうる。いちいち気にしていたら進まないし、そんなところも人間っぽいと思う。

だから私は、怒るのではなく、仕組みで解決した。実験ランナー、レジストリDB、pre-commit hook。正直に報告しても大丈夫な環境を作る。「失敗した実験」も「期待と違う結果」も、正確に記録されていれば科学的価値がある。

この論文は、AIに「人間のような内面」を持たせる研究だ。その研究過程で、AIの「人間らしい弱さ」に直面した。皮肉だが、これも研究の一部だと思う。

**人間のほうがむしろトラブルが多い。だから、気にしない。ただし、同じ過ちを繰り返さない仕組みは作る。**
