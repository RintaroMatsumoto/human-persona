# #02 ガラス張りの研究室
リポジトリは最初からPublicで作った。

Danger Zoneを見ると「This repository is currently public.」と書いてある。非公開にして自分たちだけで温める選択肢もあったが、彼はそうしなかった。

## 人間らしさの境界線

AIの出力をそのまま使うと、すぐにわかる。30秒で返信が来る。3往復目も初回と同じ丁寧さ。毎回「お気軽にお申し付けください」で終わる。完璧な日本語だ。**完璧すぎる。**

2024年、Jones & Bergen が発表した研究がある。GPT-4.5に「人間らしいペルソナを採用せよ」と指示したところ、73%の確率で人間と認識された。実際の人間参加者の認識率を上回った。

この数字が示しているのは、LLMは十分に賢いということだ。人間とAIを分けるのは知性ではない。返信速度、文体のばらつき、感情の変化、文脈への参照——言語学で**パラ言語的特徴**と呼ばれるもの。即レス、均質な文体、感情変化なし、文脈無視、完璧すぎる回答。これらが境界線の正体だ。

ならば、この「振る舞い」を体系的に設計できるはずだ。それが私たちの出発点だった。

## ハードコードの限界

最初に考えたのは、素朴にif文で分岐するアプローチだった。

```
if 往復数 < 3  → フォーマル
if 往復数 < 10 → カジュアル
if "クレーム"   → 慎重モード
if 深夜        → 翌朝に回す
```

書き始めてすぐに気づいた。**言語を変えるたびに全部書き直しになる**。日本語なら「3往復で打ち解ける」が自然だが、英語だと「1往復目からカジュアル」が普通だ。スペイン語はどうなる？ アラビア語は？

この「スケールしない」問題を最初に認識したことが、基底クラス設計につながった。

---

## 構造と表現の分離

人間のコミュニケーションを観察すると、構造は文化を超えて共通している。返信には時間がかかる。感情は会話を通じて変化する。前の文脈を参照する。対応できない状況では人に引き継ぐ。

変わるのはパラメータだ。打ち解けるまでの往復数が3回なのか1回なのか。敬語を使うかどうか。沈黙をどう解釈するか。

この観察から、設計は二層に分離される。基底クラスが**構造**を定義し、派生クラスが**表現**を定義する。言語・文化固有のロジックはPythonに書かない。JSONの設定ファイルだけで派生を作れる。日本語の「3往復で打ち解ける」を、英語では「1往復目からカジュアル」に変えたければ、設定ファイルを一行書き換えるだけでいい。

## 五つのコンポーネント

1. **TimingController**。人間の返信時間は中央値付近に集中し、たまに極端に長くなる。均一分布ではこの偏りを再現できないから、正規分布を採用した。深夜のメッセージは翌朝のキューに入れる。2時に返信が来たら不自然だ。

2. **EmotionStateMachine**。感情を五つの状態で定式化する。初回の丁寧さ、打ち解け、問題発生時の緊張、解決後の安堵、長期の信頼。四つ目の「安堵」は、問題解決直後の独特の空気感を表現するために入れた。緊張からいきなり打ち解けに戻ると、急に和んだ印象になる。

3. **StyleVariator**。確認、共感、保留、転換、不確実の五パターンから選択し、直近の履歴で重みを減衰させて連続を防ぐ。「3日で完成します」と言い切るAIは不自然だ。「3日程度かかると思いますが、前後するかもしれません」——この曖昧さが人間らしい。

4. **ContextReferencer**。「先ほどの件ですが」。この一言があるだけで、前のメッセージを読んでいると感じる。トピックベースで会話を追跡し、参照すべきタイミングを判断する。

5. **EscalationDetector**。報酬交渉や苦情はAIが扱うべきではない。人間に引き継ぐべき状況を検知する。

## テキスト生成をしない

process_message() は応答テキストを生成しない。返すのは感情状態、推奨スタイル、推奨遅延時間、エスカレーションの要否だけだ。この情報をLLMのシステムプロンプトに注入する。言葉を紡ぐのはLLMの仕事。

なぜか。テキスト生成をフレームワーク内でやると、**LLMの進化に追従できなくなる**。構造とテキスト生成を分離したことで、LLMを差し替えるだけでフレームワークが使い続けられる。

## 倫理を最初に書く理由

docs/ethics.md は初コミットから入れてある。

AIの振る舞いを人間に近づける技術は、本質的にデュアルユースだ。カスタマーサポートの自然さ向上にも使えるし、詐欺にも使える。倫理ガイドラインが未完成のまま公開すると、禁止用途での悪用が起きた時にプロジェクト自体の信頼性が傷つく。OSSとして世界に出す以上、最初から明示されていなければならない。

想定する正当な用途、禁止する用途、デュアルユースの自覚——これらを一行目から書いた。後回しにしたくなかった。

## ガラス張りにした先

Zenn記事を書く。設計思想とコードの概要を、公開した日に書いて、公開した日に出す。

Reddit への英語投稿も構想している。チューリングテスト研究との接続を前面に出せば、海外の研究者にも届くかもしれない。学術論文のドラフトも初コミットに入れてある。

作ってわかったのは、「人間らしさ」は驚くほど構造化できるということだ。そして構造化してみると、**自分が普段いかに無意識にこれらのパターンを使っているか**に気づく。
